# 🤝 Вклад в проект

## 1. Окружение разработчика

```bash
python3 -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -e ".[dev]"                             # ядро + pytest + ruff
pip install -e ".[gui]"                             # + flet, если трогаете интерфейс
```

Проверить, что всё на месте: `python check_env.py`.

Запускать код можно из любой папки — пути берутся из `autostars/paths.py`.
Для тестов и ручных прогонов в чужой папке удобно изолировать состояние:

```bash
AUTOSTARS_HOME=/tmp/autostars-dev autostars --check
```

## 2. Команды, которые должен проходить коммит

```bash
python -m pytest -q                      # 154 теста ядра/CLI/GUI-моста/настроек
python -m pytest legacy/tests -q          # 45 тестов legacy (свои зависимости)
python -m ruff check autostars tests tools check_env.py
python tools/gui_smoke.py                 # интерфейс собирается без ошибок (headless)
python -m compileall -q autostars         # синтаксис на целевой версии Python
```

Перечисленное — ровно то, что делает CI ([`ci/github-ci.yml`](ci/github-ci.yml),
включается копированием в `.github/workflows/ci.yml` — [ci/README.md](ci/README.md));
локальные прогоны должны совпадать с ним.
Форматирование импортов/лишние `noqa` правит `python -m ruff check --fix`.

## 3. Карта репозитория

| Путь | Правила |
|---|---|
| `autostars/` | поддерживаемый движок. Асинхронный, без flet-зависимостей, без чтения «своих» файлов в обход `config.py` |
| `autostars/gui/` | интерфейс. `bridge.py`/`settings.py` — логика **без flet** (тестируется), `app.py` — только вид |
| `tests/` | тесты ядра, CLI, моста и настроек. Сеть запрещена (см. §5) |
| `tools/` | служебные скрипты разработчика (gui_smoke) |
| `legacy/` | исходный AutoStars-New. Не развиваем: только правки, без которых не собираются его тесты |
| `docs/` | архитектура, безопасность, тестирование, сборка под Windows, ссылки |

Правило одного пути: если фича есть в CLI и в GUI, она живёт в движке, а GUI и CLI
— тонкие контроллеры над ним. Добавлять «вторую реализацию» окна/отчёта нельзя.

## 4. Соглашения о коде

- Python 3.10+ (CI гоняет 3.10/3.11/3.12). Никаких 3.12-only синтаксисов:
  вложенные f-strings с кавычками, `type`-алиасы и т. п.
- Строки сообщений, докстринги и комментарии — **по-русски**, в стиле остального
  проекта; метрики/ключи конфигов — UPPER_SNAKE_CASE.
- Docstring модуля начинается с того, *какую проблему* он решает — по этому
  признаку ревьюится новый модуль.
- Типы: аннотации у публичных функций; `dict`/`list`/`X | None` (PEP 585/600),
  `Optional` не нужен — ruff это проверяет.
- Никаких `print` в движке для диагностики — только `logging`; консольный хендлер
  пишет в `stderr`, чтобы `--json` на `stdout` можно было перенаправлять.
- Секреты: не выводить в логи/алерты/исключения, использовать
  `autostars.security.mask_secret`/`redact`.
- Файлы: относительные пути конфигурации резолвить через `paths.resolve_user_path`,
  не через `Path.cwd()`.
- Линтер: `line-length = 110`, правила `E,F,W,I,UP,B,C4,SIM,RUF` (см.
  `pyproject.toml`). Обходить правило можно только с `# noqa: <код> — почему`.

## 5. Тесты: как писать

Фикстуры в `tests/conftest.py`:

- `isolated_env` — временная `AUTOSTARS_HOME`/`AUTOSTARS_ENV`/`AUTOSTARS_CONFIG` +
  удаление переменных процесса, которые перекрывают конфиг. Любой тест, который
  читает/пишет `.env`, базу или лог, обязан её использовать;
- `anyio_backend` — `asyncio` для `async def`-тестов (плагин anyio).

Правила:

1. **Без сети.** Запросы к FunPay/GAMEAU/Telegram мокаются на уровне клиента
   (`httpx.MockTransport`/подмена метода). Тесты, которым нужен «живой» HTTP,
   не принимаются.
2. **Без боевых ключей.** В `env`/`.env` подставляются заглушки вида
   `fake-key-for-tests`; проверка «нет ключей» использует значения-плейсхолдеры.
3. **Опасные команды** — только до этапа подтверждения: `--test-order` тестируется
   с `--dry-run` и без `-y` (тест проверяет, что код возврата 2 и запрос не ушёл).
4. CLI-сценарии — через `tests/test_cli_smoke.py:run_cli(...)`: реальный
   `python -m autostars.main` в изолированной папке, `base=False` — режим
   «конфигурация не заполнена».
5. Тесты GUI не импортируют flet. Всё, что можно проверить без окна (мост,
   валидация настроек), — в `test_gui_*.py`; визуальная часть — `tools/gui_smoke.py`,
   который собирает все вкладки и прогоняет значения полей.
6. Если добавили/поменяли настройку — обновите **три** места: `Config`,
   `.env.example`, поле в `autostars/gui/settings.py`. Тест
   `tests/test_config_drift.py` не даст разойтись значениям по умолчанию,
   `test_gui_settings.py` — полям формы.

Новый тест — это «что сломается, если убрать этот код» в docstring. Тесты без
объяснения смысла (`assert result is not None`) не принимаются.

## 6. Конфигурация: правила изменения

`autostars/config.py` — единственная точка, где читаются `.env`/`config.json`/env.

- новый параметр = поле `Config` (dataclass) + запись в `ENV_MAP` (она же даёт
  работу ключа в `.env` и в плоском `config.json`; для вложенных секций JSON —
  `section_map`, для старых имён — `JSON_ALIASES`) + строка в `.env.example` +
  поле в GUI + тест на парсинг;
- числа парсятся через `_coerce`: некорректное значение → дефолт + строка в
  `parse_errors`, исключение не поднимаем. То же для строковых значений в
  `config.json` (`"POLL_INTERVAL": "5.0"` — допустимо);
- значения-заглушки из примера (`paste_…`, `your_…`) считаются **не заданными** и
  попадают в `issues()`;
- приоритет источников менять нельзя: процесс → `.env` → `config.json` → код
  (это позволяет systemd/Docker переопределять файл, а GUI — перечитывать `.env`).

## 7. GUI

- `bridge.engine_command()` — единственное место, где решается, как запускать
  движок (исходники vs exe). Новое разовое действие = `bridge.run_cli("--флаг")`,
  а не свой вызов клиента.
- Никаких сетевых запросов из потока окна: долгие операции идут в `run_thread`
  или subprocess, иначе интерфейс зависает на секунды таймаута.
- Поле «секрет» никогда не заполняется значением из файла; пустой ввод = «не
  менять» (см. `settings.plan_updates`).
- Логи процесса читаются из очереди `EngineProcess`, окно не открывает
  `autostars.log` на запись.

## 8. Сборка и релиз

- `autostars.spec` — только CLI (`AutoStarsBot.exe`). GUI пакует `build.bat` через
  `flet pack` (Flutter-рантайм в обычный spec не кладётся).
- `.env.example` и `config.example.json` попадают в дистрибутив через `datas` /
  `--add-data`; иконка — `ico.ico`, если лежит в корне.
- Версия: `autostars/__init__.py:__version__` **и** `project.version` в
  `pyproject.toml` — менять вместе (иначе `--version` врёт), дата — в `CHANGELOG.md`.
- Релизный чек-лист: `pytest` зелёный (ядро + legacy) → `ruff` чистый →
  `gui_smoke` OK → `python autostars_bot.py --check` на чистом `AUTOSTARS_HOME` →
  `build.bat` на Windows собирает оба exe → тег `vX.Y.Z` + release с `dist\*.zip`.

## 9. Процедура PR

1. Ветка от `main`, одна логическая задача на PR.
2. `git status` — в диффе не должно быть `.env`, `autostars.db`, `autostars.log`,
   `.venv/`, `__pycache__/`, `build/`, `dist/`.
3. Описание: что и почему, как проверить (команды), затронута ли конфигурация/схема БД.
4. Если тронуты деньги (maxCharge, идемпотентность, статусы) — тест обязателен, а
   в описании — строка «реальных покупок не выполняется: …».
5. CI зелёный. Legacy-джоб может быть жёлтым (`continue-on-error`), но падение
   его тестов — повод починить или удалить код.

## 10. Чего не делать

- Не возвращать в корень второй `main.py`/`bot/` — для исторического кода есть `legacy/`.
- Не добавлять зависимости в `requirements.txt` в обход `pyproject.toml`.
- Не «улучшать» GUI отдельной бизнес-логикой (свои расчёты, своя база, свои
  запросы) — всё это должно быть в движке и доступно из CLI.
- Не тащить в логи и алерты полные ответы API и cookies: достаточно кода ответа,
  номера заказа и `chargedAmount`. Никнеймы и chat_id покупателей — только там,
  где без них непонятно, о каком заказе речь.
- Не менять схему БД без миграции в `DBManager._migrate_orders_table()` и теста на
  старой базе (пример — `tests/test_statistics.py::test_legacy_db_migration`).
